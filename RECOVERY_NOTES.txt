WHAT HAPPENED

1. The owner authorized unlocking and its factory reset.
2. fastboot flashing unlock returned OKAY. Read-only queries reported
   unlocked:yes and secure:no.
3. The assistant issued fastboot reboot bootloader as a persistence check.
   The unlocked state was confirmed again, then fastboot reboot was issued.
4. The TV subsequently showed the Google TV logo briefly and went into
   standby/powered off. It did not merely remain on a black Fastboot screen.
   No replacement firmware, boot, recovery, or bootloader image had been
   flashed when this failure began.
5. After the recovery procedure below and a stock factory reset, the owner
   confirmed reaching setup again.

LIKELY CAUSE, AND WHAT IS NOT PROVED

In the inspected V122 MBOOT implementation, unlocking writes boot-recovery
and recovery\n--wipe_data\n into the bootloader control block (BCB), raw-erases
userdata, and changes the lock state. Recovery is then expected to finish
formatting the erased data partition.

The reboot-bootloader handler overwrites the BCB's boot-recovery command.
The bootloader consumes that replacement request; a later ordinary reboot
does not restore the original request. Our extra reboot into the bootloader
therefore likely diverted the recovery wipe that should have followed unlock.
The stock factory reset restoring boot supports this explanation.

During the failure investigation, we had neither a dump of the installed V109
bootloader nor the original boot-failure log. A V109 bootloader dump is now
available from the later backup, but its wipe/reboot implementation has not
yet been reanalyzed here. The cause remains an evidence-backed hypothesis,
not a proven V109 diagnosis. See research/unlock-recovery-analysis.md.

PREVENTING A REPEAT

- Treat an unlock and its recovery wipe/format as one operation. Immediately
  after unlocking, verify state with read-only getvar queries only. Preserve
  the pending recovery request and let the wipe finish before testing any
  further boot modes. Do not insert reboot bootloader as a persistence check.
- A normal reboot directly after unlocking should preserve the pending
  boot-recovery request in the inspected implementation. This preventive
  sequence is inferred from V122; we did not unlock this TV a second time to
  test it. Do not repeat flashing unlock on an already-unlocked TV.
- Confirm successful normal boot before experimenting further. Record lock
  state again from the running system when ADB is restored; another unlock
  or immediate reboot cycle is unnecessary.
- Preserve the working recovery artifacts listed below. Before experimental
  boot/bootloader image writes, establish a readback route and preserve this
  unit's exact images and unique calibration data. Fastboot USB readback and
  temporary fastboot boot were not available in the inspected command table.
- Do not use relocking or a blind raw metadata/userdata erase as a remedy.
  Raw erase is not recovery's filesystem/encryption preparation.

WHAT FAILED OR WAS NOT SUFFICIENT

- Holding physical Power before connecting mains did not start this TV.
- An empty ZIP reached Installing updates -> Error -> restart. It established
  entry to stock recovery, but did not perform an update or repair data.
- Generic Power+Volume-Up advice did not produce a usable menu. The owner had
  about three seconds to swap USB devices; that was not a practical solution.
- In inspected TCL V122 recovery, an update error can exit recovery even when
  text is visible. Generic AOSP advice about revealing text to keep the menu
  open was not sufficient for this TCL build.
- A clean fastboot reboot recovery was accepted, but the owner saw No command
  briefly and then a restart. It also needed an explicit --show_text request.
- Fastbootd's screen worked, but the TV did not enumerate over USB in that
  mode, including after a cable reconnect. The normal remote worked there.
- Enter recovery from our specially triggered Fastbootd session was avoided:
  in V122 it retains the original update arguments in the same process.
  That path was not tested on V109. Reboot to bootloader worked instead.

RECOVERY PROCEDURE THAT WORKED ON THIS UNIT

A. Reach a persistent Fastbootd menu through the prepared USB stick.

The approved 32 GB PNY stick has one MBR/FAT32 partition, label originally
TVRECOVERY, UUID 6ECB-21F4. It contains two identical 22-byte empty ZIPs:
  update_signed.zip
  V8-T221T04-LF1V109.000732.zip
Their SHA256 is:
  8739c76e681f900923b900c9df0ef75cf421d39cabb54650c4b9ad19b6a76d85
These names do not identify firmware payloads; the archives contain no files.

The important change is the 11-byte volume label, hexadecimal:
  0a2d2d666173740a202020
Equivalent bytes: LF, --fast, LF, three spaces.

MBOOT's inspected root-label path copies its first eight bytes into a
newline-delimited recovery argument field. This adds --fast, recognized as
an unambiguous abbreviation of --fastboot by recovery's main option parser.
Actual V122 MBOOT instructions and libc getopt_long were exercised offline
with Unicorn, with hardware access and simple libc operations stubbed.
The owner then confirmed the trigger worked on the actual V109 TV.

With the TV plugged into mains and in standby, insert the prepared stick.
Hold the TV's physical Power button; release it when the LED blinks, using
the same successful USB-upgrade entry procedure. Fastbootd should stay open.
Use the normal remote to choose Reboot to bootloader. Remove the stick and
connect the USB-A cable to the laptop. A black bootloader screen is expected;
verify it through USB enumeration rather than assuming the TV powered off.

B. Identify bootloader Fastboot and explicitly request a visible recovery.

Bootloader USB was 0e8d:5000. Its serial text was garbled, so commands selected
the USB path shown by sudo fastboot devices -l. The observed path was
usb:3-1.3; re-identify it each session rather than assuming it is unchanged.

Read-only checks immediately before writing:
  product: C06_eu
  is-userspace: no
  unlocked: yes
  partition-size:cache: 0x06400000
  partition-type:cache: ext4
  max-download-size: 0x30000000

The prepared assets/research/recovery-probe/cache-menu.img is exactly 104857600
bytes (100 MiB). It is an ext4 cache filesystem whose /recovery/command is
exactly the 12 bytes --show_text followed by newline. It contains no wipe
command. The file has the stock cache_recovery_file SELinux label.

Image SHA256:
  0f2f01c087e4fa0df4ce97b5f70b5c966edee994787c3577a3ba0fc1013bedad

It was created with mke2fs.android using the extracted stock recovery's
mke2fs.conf, 4096-byte blocks, 256-byte inodes, and initialized journal/inode
tables, then populated with e2fsdroid. e2fsck -fn passed; debugfs verified
command contents, ownership, SELinux xattr and stock-compatible ext4 features.
Do not use a newer host's default filesystem features without checking them.

Commands that succeeded, from /home/eduardo/tv_hack:
  sudo fastboot -s usb:3-1.3 flash cache assets/research/recovery-probe/cache-menu.img
  sudo fastboot -s usb:3-1.3 reboot recovery

These are recorded commands, not unconditional instructions for another TV:
check the target, unlocked state, cache size/type, and image hash first.
Flashing this image replaces cached files and old recovery logs. The owner
was told this and instructed us to keep going. Both sending/writing cache
and rebooting recovery returned OKAY. Device readback was unavailable; the
owner's subsequent persistent recovery menu is the functional confirmation.

C. Complete the stock factory reset.

The owner confirmed the Android Recovery menu stayed open and listed
Wipe data/factory reset. Using the normal remote, select that option, confirm
the reset, wait for completion, then select Reboot system now. The owner
confirmed the Google TV setup screen appeared afterward.

This factory reset erases user data/settings. It was already authorized in
this session. That authorization is not blanket consent for a different
owner or a future reset after valuable data has accumulated.
