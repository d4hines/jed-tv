OFFLINE UNLOCK ANALYSIS OF V033, NOT INSTALLED V013

Extracted mboot.img SHA256:
  dd2c03211bbe17ed8b66d923611f46f134ac8005f64c2d8f5a598502376379da
It identifies as bootloader 01.01.260423. The installed version remains
01.01.250814; do not claim binary identity or tested unlock success.

Mapping: virtual address = file offset + 0x273fdc00; ARM code starts at
file offset 0x2400 / virtual 0x27400000. The preserved disassembly helper
was adapted from the previous offline tool without modifying the original.

USB Fastboot initializes at 0x274c5728. It computes table base 0x276a4ca8,
then registers "flashing" using the pointer at base+0x34c = 0x276a4ff4
(file offset 0x2a73f4), whose value is 0x274c3f14.
See mboot-init-prefix.txt, mboot-registration.txt and mboot-flashing-handler.txt
in the V033 firmware directory.

That handler obtains current unlocked state via 0x274b7bd8. Its
get_unlock_ability branch returns lock or unlock based on that state. It is
not a separate OEM permission check in this inspected implementation.
The live installed bootloader's INFO lock response is consistent with this.

The ordinary unlock branch at 0x274c4078 compares "unlock", requires current
locked state, prints "wipe user data", calls 0x274b701c, then calls the state
writer 0x274dee40 with zero. No separate OEM setting, token check or on-screen
confirmation is called in this handler. It then sends Done!! without checking
the state writer's return. A later live read-only unlocked query is necessary.

Wipe helper 0x274b701c configures misc, writes 85 bytes from 0x276a2a96 to
offset zero, then executes "mmc erase.p userdata". The 85-byte constant is
boot-recovery, padding, then recovery\n--wipe_data\n. This is the same pending
recovery-wipe design encountered on the older firmware. See mboot-wipe.txt.

ASSESSMENT AND NEXT OPERATION

The ordinary Fastboot unlock route is a well-supported candidate for this
unit; the newer same-platform firmware retains the familiar implementation.
Unlock success on the installed V013 remains untested. Android's
sys.oem_unlock_allowed=0 does not by itself prove rejection by this handler.
Root is not a prerequisite for issuing the bootloader unlock command.

An actual unlock erases the new TV's user data/settings and changes persistent
state. This session performed only read-only Fastboot queries. If the owner
chooses to unlock, re-identify the USB path, check unlocked:no, issue ordinary
flashing unlock once, check unlocked using getvar only, and allow the pending
recovery wipe to complete. Do not insert reboot bootloader after unlocking.
Use normal reboot for the pending recovery flow and wait for normal setup.
This planned sequence is inferred from V033, not tested on V013. Do not issue
unlock_critical, relock, flash old cache images, or switch slots as part of it.
