Experimental stock-recovery entry probe for TCL 32Q3K

update_signed.zip is a 22-byte empty ZIP, containing only an end-of-central-
directory record. It contains no files, updater executable, scripts, firmware,
or signature. It is deliberately not an installable update.

The ZIP has been copied to the owner's USB stick and trials are recorded
below. The following is static analysis of the official
V8-T221T04-LF1V122 MBOOT, not proof of the installed V109 implementation or a
hardware-tested procedure.

Evidence (runtime addresses; file offset = address - 0x273fdc00):

* get_boot_mode_from_keypad at 0x274211bc recognizes a long logical 0xd5
  press as USB-upgrade mode. Mapping this to the Q3K's physical button and
  exact timing is still unverified.
* do_bootcheck at 0x27421a48 tries custar. If that returns -1, it runs
  ota_zip_check and, on a result other than -1, boots the installed recovery.
* custar starts by saving upgrade_status=ongoing. With no recognized firmware
  files, its 0x274928b0 path clears force_upgrade, sets upgrade_status=NULL,
  saves the environment, and returns -1 at 0x27492ab8. This is an environment
  write even when no firmware payload exists.
* ota_zip_check_usb at 0x27491340 first attempts filenamefind with the prefix
  from ForceUpgrade_path and suffix .zip. It may save ForceUpgrade_OTAPath.
  If that variable is absent, the fallback is /update_signed.zip. A stale
  saved ForceUpgrade_OTAPath could prevent this fallback from being used.
* The call to check_file_partition at 0x274916c4 only checks that a file can
  be read. The latter constructs fatload usb ... <filename> 1, i.e. a
  one-byte RAM read, at 0x2741d96c. It does not validate ZIP content.
* At 0x274917e0 onward, the OTA handler constructs a 2048-byte boot control
  message: boot-recovery, with recovery arguments for --update_package,
  --label, and --uuid. It writes this to misc at 0x2749197c. This replaces
  existing recovery arguments, including a potentially pending data wipe.
* boot_mode_recovery at 0x2741fb68 uses readKL recovery; bootKL, loading the
  installed recovery partition rather than a recovery image from USB.

Thus the hypothesis is that a nonempty but payload-free ZIP can request
installed recovery, where package verification should fail. This does NOT
establish that the recovery menu will remain visible. AOSP Android 11
production recovery can reboot after an error if text UI is not visible;
TCL's custom V109 recovery has not been extracted or checked. AOSP's
button-limited UI supports a long press to show text, but that behavior is
also unverified on this TV.

Use only the empty probe ZIPs described here at the root of a FAT32 USB flash
drive, with no real firmware/update files. Do not rename these ZIPs to .bin,
.pkg, or .img. Disconnect
the USB-A-to-A laptop cable while the flash drive is attached. No storage
formatting, device erases, relocking, or replacement-firmware flashing is
part of this probe. Existing recovery can subsequently perform the already
authorized factory reset if a usable menu is reached.

Offline V122 recovery analysis (not a dump of the installed V109):
* Downloaded official OTA vendor.new.dat.br by ranges, verified ZIP CRC,
  reconstructed vendor.img with complete block coverage, extracted
  vendor /etc/recovery.img and its gzip CPIO ramdisk. Recovery image SHA1
  e0a9e830a8b3c22164b456c6f2a4d261f4f82e59 matches install-recovery.sh.
* librecovery_ui_ext.so's TCL UI uses base RecoveryUI::CheckKey.
  Base CheckKey at 0x1c2f8 toggles text when KEY_UP (103) or KEY_VOLUMEUP
  (115) is released while KEY_POWER (116) is held on three-button devices.
  Long press instead toggles text on button-limited devices.
* minui input implementation has inotify-based hotplug: ev_init watches
  /dev/input for IN_CREATE; inotify_cb at 0x1d724 opens event* devices,
  checks supported input event types and registers the input callback via
  ev_add_fd. Thus a keyboard need not be connected at recovery startup in
  V122. V109 and this keyboard's actual behavior remain untested.
* IMPORTANT correction to earlier AOSP-based menu advice: actual TCL
  start_recovery error/corrupt status path at 0x17236..0x1725e sets the error
  background, waits five seconds if text is hidden, then goes to cleanup
  at 0x18268 regardless of text visibility. PromptAndWait entry at 0x1727e
  is gated on status == 3 (INSTALL_NONE) and visible text. Therefore
  showing text during a failed update is NOT a demonstrated way to keep
  this TCL recovery open or reach the reset menu. It may only expose logs.
* second_udisk_removed_notice at 0x4157c can instead enter an indefinite
  'Wait for external storage insert' display on certain removed-media
  errors. To avoid changing the initial package-read failure, a keyboard
  swap test should be made AFTER the Error display appears, not while
  Installing Updates is still being processed.
* Proposed diagnostic input test: reproduce the successful USB entry,
  release physical Power at the blink, wait for Error, swap the empty-ZIP
  stick for keyboard, aim remote at TV and hold remote Power while tapping
  and releasing keyboard Up, then promptly release Power. Text may appear
  only briefly before reboot; photograph if it does. This is an experiment
  based on V122, not a confirmed V109 recovery shortcut or repair.
* A possible physical-button keycode mismatch remains speculative: app
  keypad config values are not sufficient to establish Linux input codes.
