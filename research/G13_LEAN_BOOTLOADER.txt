KernelConfig holds the kernel entry, FDT, initramfs address/length and secure
message address. The success callback is invoked once, after preparation, and
is specialized to direct code rather than allocated or stored. The actual
kernel/FDT values are now carried through both stack transitions to the jump.
No parser, copying loop, cache traversal or policy moved into assembly.

Unsafe.MemoryM colors physical RAM. Unsafe.HardwareM colors MMIO, CPU, UART,
secure calls and handoff. Every raw BaseIO extern is private; public operations
return the appropriate monad. liftMemory is explicit and one-way. Runners
discharge a color at reviewed outer adapters only. A Permission proposition
keeps colors distinct while allowing the compiler to erase them. It is not a
proof of ownership or a security boundary against deliberately bypassing code.
The generic core cannot import these physical operations; the source audit
enforces that separation. It also runs unchanged under pure ReaderT/StateM.

Supported G13 entry: leanboot_os_start at image offset zero. Seven DSL
instructions preserve the caller and select a private stack ending 26340000.
Lean admission checks require ARM SVC, IRQ/FIQ masked, aligned/private SP and
SCTLR 00c0181d. Failure returns 26 before UART or image access. Valid coherent
code, mapped RAM, and an aligned caller stack with 8 writable bytes are still
bootstrap prerequisites; these cannot be discovered safely after bad entry.
The full-image tests measured 584 bytes of private-stack use. This is measured
coverage, not a formal worst-case proof. The complete contract is in
src/bootloader/Unsafe/CONTRACTS.txt.

Validation occurs before destructive vendor ramdisk compaction. Invalid
length/config/digest metadata is rejected before any output write. FDT editing
may modify its private scratch before rejecting a malformed recipe; such a
failure never reaches the success callback or hardware commit. Successful
preparation still overwrites the staged vendor header, so raw inputs must be
reloaded before retrying.

Compressed serial transfers
----------------------------
The owner requested compression for substantial serial transfers. Exact MBOOT
supports lz4 -d <src_addr> <src_len> <dest_addr> <dest_len>, all hexadecimal.
It expects a raw LZ4 block, not the framed .lz4 file format or a size prefix.
There is no unzip command. Host upload now compresses inputs >=1024 bytes when
that saves at least 64 bytes, checks a local round trip, uploads to 26100000,
checks compressed CRC, invokes lz4 and checks the exact decompressed CRC.
Source padding accommodates the stock decoder's word reads. Its source length
is an output/consumed count rather than an enforced input bound, so only trusted
host-generated and CRC-verified blocks may be passed to it.

check-transfer.py ran 14 inputs through the exact saved ARM decoder, including
full loader/control data, 64 KiB repeated and incompressible inputs, checking
read/write bounds. Current TV uploads passed: loader 18992 -> 12651 bytes,
control 3136 -> 1927 bytes, plus 16 zero bytes after each compressed block.
Compression is a MBOOT bootstrap transport; no stock decoder is called by Lean.

Word-by-word transfer still cost 79.87 s despite compression. Bulk upload now
uses loady and lrzsz sb, routed through the existing Screen session's exec !!
filter. Neither helper opens another serial reader. Starting the sender before
loady avoids losing the initial handshake; waiting for the final MBOOT prompt
plus its receiver drain avoids losing the next command's tail. The wrapper
has a 45-second bound and restores the original terminal settings. Transfers
below 1024 bytes retain word commands; incompressible bulk data uses YMODEM.
One complete loader/control transfer took 12.22 s including decompression and
CRCs, about 6.5 times faster than the compressed word-command transfer. The
record is secure-trial/ymodem-transfer.json; individual sender/CRC results are
in ymodem-*/. check-serial.py passed a 78187-byte round trip over two connected
PTYs including every byte value, checking restored terminal settings. That
test never accesses the TV. Prefer Ethernet ADB once Linux is up.

Entry contract
--------------
MBOOT's ARM-mode go calls entry(argc-1, argv+1). The probe currently ignores
the arguments. It borrows an 8-byte-aligned caller stack, preserves r4-r11
and SP, and returns through LR. The current compiled-Lean probe uses 8 bytes
of stack in the emulator; the earlier hardware probe used 16. It leaves
CPU mode, interrupt masks, MMU and cache controls alone.
It relies on stock DRAM, clocks and UART configuration already being ready.

Only the Unsafe primitives touch hardware: a word read at UART status 0x1f201328
and a byte store at TX data 0x1f201300. The address/widths are grounded in
this unit's boot0 routine at file 0xe304; the live MMU map and successful
hardware output establish them at the tested MBOOT handoff as well.
Main.lean converts status bits 5/6 into the Lean core's ready/idle flags.
Lean requests the exact 14 bytes "LEANBOOT RAM\r\n", waits for the
transmitter to empty, then requests return 0. Stalled ready/drain polling
returns 1 after 1,048,577 unsuccessful reads in that phase. Corrupt core
state requests return 2. This bounds loop iterations, not wall time if an
MMIO access itself hangs. No receive, DMA, flash, environment, slot or fuse
operation exists in the payload.

Getting control earlier
-----------------------
The demonstrated order is:
  BootROM -> stock DRAM/secure loaders -> stock MBOOT initialization
  -> MstarProcess phase 1 -> interrupted autoboot -> our Lean RAM probe
  -> return to MBOOT -> normal reset -> existing native Linux startup.

This skips neither stock DRAM training nor the secure loaders and does not
install an automatic jump. It establishes the architecture, ABI and safe
return boundary before attempting earlier takeover. The MBOOT log already
places its banner around 448 ms and driver-init marker around 504 ms on
its own clock. The manually paused/uploaded probe is not a power-on speed
measurement, and those markers are not wall-clock boot-to-home timings.

Exact main_loop analysis matters for the next change: MstarProcess runs at
linked 0x274c9604 before the abort check, and MstarToKernel at 0x274c96ec
before the eventual bootcmd execution at 0x274c9748. Simply replacing
bootcmd is therefore not demonstrated to bypass the vendor's phase-2
kernel path. No generic U-Boot preboot recipe has been applied.

Next work: own the image intake, RAM layout, boot-data construction and Linux
handoff in Lean, rather than delegating readKL/bootKL to MBOOT. Move the
handoff earlier only after tracing the initialization we actually need.
Earlier persistent
injection or replacing authenticated MBOOT executable code is a separate
step: logo-asset modification did not establish code-signature acceptance,
and independent BootROM recovery/spare-copy fallback remain unverified.

Independent loading findings and remaining work
-----------------------------------------------
The latest owner direction is to reverse engineer and replace vendor loader
logic wherever feasible, keeping the few irreducible unsafe operations in
one auditable boundary. Ordinary Lean BaseIO lowers to scalar C functions
with this compiler; there is no reason to put loops, parsers or device
protocol sequencing in the ARM DSL. No router runtime was needed.

Exact stock fixtures independently decoded by the Lean ARM code:
  boot_a:        kernel at 4096, length 15871916; generic ramdisk absent
  init_boot_a:   generic ramdisk at 4096, length 2032630
  vendor_boot_a: vendor ramdisk at 4096, length 18128651
                 DT container at 18132992, length 42446
                 fragment table at 18176000, length 108
                 bootconfig at 18178048, length 63
  DT container:  one 32-byte Android DT-table entry after a 32-byte header;
                 actual FDT at container+64, length 42382
The table uses magic d7b7ab1e and big-endian fields, not a legacy uImage
header. The parser verifies the container rather than blindly skipping 64.
Only the observed single platform fragment with wildcard board IDs and
single wildcard DTB are supported. Other selection rules remain unimplemented.

Header load addresses are not a ready-to-use RAM plan. In exact readKL_dtb,
linked 0x2745241c sets ramdisk base 0x24000000; 0x274524f8..0x27452518 copies
the vendor fragment and increments its length; 0x27452660..0x2745267c appends
the generic ramdisk there. For these stock sizes the combined ramdisk ends
at 0x2533a301, overlapping the first probe's 0x25000000 address. The active
modified init_boot has a different ramdisk size and must be measured too.
No kernel-capable payload should inherit the tiny probe's address blindly.
See assets/research/g13-startup-trace-20261101/mboot-ramdisk.txt.

The exact command table resolves bootKL to linked 0x27456d6c. It selects an
image/auth address (v4 path through 0x2742bf7c), invokes 0x27452ae8, formats
"bootm 0x%x", then dispatches the string at 0x27456ea0. Replacing bootKL
therefore requires tracing the remaining bootm/FDT/CPU work, not just its
small command wrapper. Fresh disassembly is saved in
assets/research/g13-leanboot/bootkl-disassembly.txt; regenerate with:
  nix develop .#bootloader -c python3 research/recovery-probe/inspect-g13-startup.py mboot 0x5916c 0x680
These are linked addresses, not live jump targets.

Next components are an independent read-only image transport (own UART
receive protocol or a traced FCIE/eMMC reader), checked placement outside
loader/stack/reserved regions, full FDT validation/editing and bootconfig
assembly preserving this TV's native startup settings. Trace and replace
CPU/cache/DMA preparation before adding the final Linux transfer. Cache
iteration belongs in Lean; only the individual CP15/barrier operations
belong in Unsafe. No such operation or jump has been added speculatively.

The installed early ROM/DRAM/secure loaders and the initial RAM-upload
mechanism remain dependencies. The earlier test used MBOOT upload commands
and cache helpers; this refactor does not make that bootstrap independent.
It does remove MBOOT services from all implemented payload logic.
