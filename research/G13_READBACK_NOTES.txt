CONFIRMED MECHANISM

An ordinary locally signed APK targeting API 32 can call the installed
MediaTek factory HIDL service. This G13 firmware explicitly allows the
untrusted_app_32 SELinux domain to find hal_tv_tvfactory_hwservice and call
hal_tv_tvfactory_default. ADB shell has no such permission. This explains why
the earlier shell/app_process probe failed even though an installed app works.

Relevant live vendor policy (preserved in assets/research/new-tv-20261031T183329Z/readback-probes):
  (allow untrusted_app_32_34_0 hal_tv_tvfactory_default (binder (call transfer)))
  (allow untrusted_app_32_34_0 hal_tv_tvfactory_hwservice (hwservice_manager (find)))
The live platform seapp_contexts assigns targetSdk32/33 regular apps to this
domain; targetSdk34 uses a different domain. The installed tcl.adapter shared
library supplies the generated factory interface classes.

The APK uses:
  vendor.mediatek.tv.mtktvfactory.V1_0.IMtkTvFApiSystem
  getService("default", false)
  a_hidl_a_mtktvfapi_sys_read_file_byte(path, length, long_offset, callback)
This generated proxy sends HIDL transaction21 and returns a byte vector and
status. Status0 and exact requested byte counts are required for raw reads.

The actual installed native implementation preserves the 64-bit offset
through MI_FS_Fseek -> MsFS_Fseek -> fseeko64, including on this ARM32 build.
It checks seek success before reading. This matters because super crosses
the 2 GiB boundary. See g13-readback/offset-width-analysis.txt and the saved
disassemblies/libraries for the verified call chain.

A fixed probe read /proc/self/status through the HAL and observed uid/gid0
in the service process, domain u:r:hal_tv_tvfactory_default:s0. The app itself
ran as uid10108 in untrusted_app_32. The helper did not execute root shell
commands, change SELinux policy, or modify firmware partitions. adb root still
reports production-build refusal, and direct shell block reads are denied.

The service can read mmcblk0, both hardware boot areas and live sysfs geometry.
The first full MBOOT capture matched an independent second source read:

TOOLS AND GUARDS

g13-readback/ReadbackActivity.java: initial fixed diagnostic probe.
g13-readback/ServerActivity.java: bounded read-only bridge; no write/exec API.
g13-readback/package-apk.py: minimal binary manifest, targetSdk32, tcl.adapter.
g13-readback/build-helper.sh: builds and locally signs the bridge APK.
g13-readback/client.py: authenticated ADB-forwarded socket transport.
g13-readback/dump-stock.py: geometry checks, capture, verification and manifest.
g13-readback/verify-backup.py: independent host/chunk/coverage verification.

The helper has no Internet permission. Its random abstract Unix socket and
per-launch UUID token are announced to authorized ADB in the TVReadback log
tag. adb forward binds a temporary host port; the client removes that mapping
when it closes. The helper is kept foreground with the screen awake. It does
not start on boot, install su, or alter boot/recovery images. Its only ordinary
file writes are small files inside its own Android app data directory.

The host and app both require the exact V013/AU13 fingerprint. The app accepts
only bounded sysfs text reads and aligned raw reads from mmcblk0/boot0/boot1.
Raw eMMC reads stop before userdata's live start; RPMB is not accepted. It
never accepts a block-device output path or shell command. Requests are at
most64MiB, HAL reads are256KiB, and the host currently captures32MiB chunks.
Only one dumper may run; a host flock enforces this for the supplied script.

The host builds its map from current /dev/block/by-name links and the HAL's
reads of /sys/class/block/{node}/{start,size}. It checks all51 physical
partitions, excludes userdata, checks bounds/overlaps, then captures the other
50 named partitions, both4MiB hardware boot areas, and the first2MiB of eMMC.
Expected current plan:53 images,3359MiB. These sizes are observed values, not
constants to reuse on another model. No eMMC tail inside userdata is captured.

    --target 18ACC22D1C47 --output assets/backups/g13-v013-stock-new

Use a new output directory. --resume can resume an interrupted capture only
when its identity, geometry and plan match. Previously completed images are
rehashed on the laptop; an incomplete image restarts, preserving its partial
under an .interrupted timestamp. Never run the old G06 dumper on this TV.

The JDK path in build-helper.sh is the tested Nix store path; if garbage
collected, supply a JDK supporting javac --release8. The saved R8/D8 JAR is
8.3.37. The small Android4.1 compile-stub JAR is only a host build dependency:
the APK itself targets32 and runs against the TV's actual Android14 APIs.
Its SHA256 is checked by the build script. A binary XML manifest avoids the
x86-only aapt package on this ARM64 NixOS host. Android installation and
apksigner both accepted that manifest. The signing key is a new local helper
key, unrelated to TCL's platform signing key.

VERIFICATION AND LIMITS

For every captured chunk:
  1. HAL reads fresh bytes; the helper hashes exactly the streamed bytes.
  2. The laptop verifies length and SHA256 during transfer.
  3. A separate HASH request rereads the same source range through the HAL.
  4. The host compares that second source SHA256 to the transferred bytes.
At image completion, the file is fsynced, renamed from .partial, protected
mode0400, and independently reread on the host for a full-image SHA256.
The backup directory is mode0700 because calibration/certificate partitions
contain device-specific data. All paths and chunk results are in manifest.json.
