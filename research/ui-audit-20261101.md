# TV UI audit in QEMU, 2026-11-01

Branch `codex/opus-ui-audit` (from main `371b06a`). Offline, headless ARM32
QEMU only: no TV, adb, fastboot, serial, flashing or host audio. Evidence is
under `assets/research/ui-audit-20261101/` (curated) and
`assets/build/ui-audit/<session>/` (every screenshot, serial log, fixture
request log).

## What was tested

Runtime: the **embedded PID1 launcher** (the real `hello-pid1` REPL build,
sha256 `2a12f316…`, behind the G06 syscall trampoline), Linux 6.18.57 virt
surrogate kernel (`996d7306…`), virtio-gpu 1280x720, virtio-keyboard,
virtio-sound into a WAV file. User networking with `restrict=on`; the guest
reaches only the local fixture server. Not the TV kernel, panel, display
service or audio service.

|---|---|---|---|
| original (main `371b06a`) | `8d869820…` | `65a0d48f…` | `73dd3f28…` |
| fixed (this branch) | `8063c985…` | `6ae997c8…` | unchanged |

**YouTube data is fixtures, not YouTube.** The fixture server (`tools/ui-audit/session.py`)
returns the generated 16 s demo media for every video ID, plus labelled
`[fixture]` search results: six playable, one unplayable, a live entry without
length (filtered by the client), and the queries `none` (0 results), `fail`
(HTTP 500) and `slow` (4 s). Thumbnails are absent: the Rust app fetches them
from `https://i.ytimg.com`, which has no DNS offline (blank tiles, about 5 s
of resolver timeout per search).

Method: each flow was driven with QMP key events (`tools/ui-audit/session.py run`),
screenshots were viewed one by one or as contact sheets, and serial/PID1
logs were checked. Some flows were repeated after fixes.

## Defects fixed (local commits)

Each fix has a before/after image in `assets/research/ui-audit-20261101/before-after/`
(red = before, green = after) and an automated case in `tools/ui-audit/check.py`.

**D1. The video player froze on its last frame after a seek near the end** (`c68562c`, `04e6280`).
Repro: Demo video, Right three times about 1.5 s in (0:11, 0:15, 0:15). The
picture stayed on frame 382 with a stale "+10 s" bar for over a minute; only
Back recovered (`1-player-end-freeze-t0/t3.png`). Cause, from instrumented
logs: audio ends at 16.024 s, the last frame is stamped 16.042 s; after
audio finishes its clock stops, and `present()` waited for a time it could
never reach. The original binary froze in all three QEMU tries with this
sequence. It is still a race with the audio drain, so it may also hit natural
ends on slow hardware. Fix: stop pacing once audio is done (`frame_due`,
unit-tested).

**D2. Search status text was cut at 28 characters** (`6ed5130`). The help
line lost "keys work too", zero results lost ")", and errors lost their cause:
"Search failed: search HTTP 5"; offline it would read "Search failed: failed
to lo". Fix: word-wrap the column (up to five lines), with a unit test.

**D3. A long query ran off the query box** (`6ed5130`). The box showed the
last 60 characters but fits 44, so the cursor and newest input were off
screen. Fix: show the newest characters that fit.

**D4. A failed search kept the previous query's results** (`6ed5130`): they
could still be focused and played under the new query. Fix: clear them.

**D5. Choosing a search result that could not play gave no feedback**
(`71d664c`). The search screen came back unchanged, so OK looked ignored (the
hub already showed "Loading…"/"Could not open"). Fix: show "Opening …",
then "Could not play: …" on failure, and restore the search summary after a
successful play. Applies to the app and browse mode.

**D6. Back could not leave the Doom LAN lobby** (`26bd225`). The lobby says
"BACK: LEAVE", but keys went to the menu responder first, and the closed menu
takes Escape to open itself. Back toggled the main menu over the lobby text;
only Quit Game or Home got out. A joiner still searching had no session, so
leaving was never processed. Fix: route OK/Back to the lobby while no menu is
open, and process leaving before a session exists. Verified for both host
and joiner (`sheet-doom-lobby-fixed.png`).

## Noted, not fixed

* **N1** About lists "46 syscalls, 11 ioctls"; ytplay installs 54 and 12.
  Hard-coded text in `src/tvinit/src/lib.rs` (embedded in PID1), so it needs a
  PID1 rebuild; it could be computed from `platform::seccomp`. The
  "FFmpeg decoder" line becomes stale if the Lean decoder merges.
* **N2** Presses during an app's first frames are forwarded to it (double OK
  skips Slides' title). Defensible; flush input until the first frame if unwanted.
* **N3** Search runs on the UI thread. Input is queued for the whole request
  (about 9 s with the slow fixture and DNS timeouts): two Backs during it land
  on hub without results being seen. Home is unaffected (PID1).
* **N4** `assets/build/tiles/slides.rgb` predates the Lean Slides look;
  regenerate with `tools/make_tiles.py`.
* **N5** Doom's "Choose game type" submenu is small red text on the red title
  art (`f10`). The overlapping "NEW GAME" header is vanilla behaviour.
* **N6** The Pause key is mapped in `Doom/TV/Keys.lean` but `buildTiccmd`
  ignores it (documented). The End Game prompt "PRESS OK OR BACK." doesn't say
  which key confirms.
* **N7 (for the coordinator, `src/pid1/src/volume_control.rs`)** "MUTED" is
  shown whenever the level is 0, including volume-down to 0. Volume Up while
  muted steps up from 0 instead of restoring the saved level. Autorepeat at
  100% rewrites the file, republishes the OSD and logs every 38 ms
  (13 identical `key=115 gain=0.0300` events in 0.5 s). Percent steps are
  8.33% (25, 33, 42…).
* Long search titles and the hub's 70-character status are hard-truncated
  without an ellipsis.

## Lean YouTube app (report only)

During the audit the shared parent build `ytplay` was replaced by the Lean
YouTube app from the review branches (`3e766e75…`, logs `ytlean:`). It is
not on main and belongs to the main-c6 track, so I only explored it
(session `lean1`, `sheet-lean-*.png`). The Back chain is one step per press.
Errors appear in a full-width status line, so D2 does not occur there, and
playback ends after seeking past the end, so D1 does not either. Findings:
* the stale-status bug behind D5: after "Not playable: …", a later
  successful play and even leaving and re-entering Search keep the old error
  (`L11`, `L12`, `L14`);
* seeks are labelled past the duration (0:22, 0:32 on a 0:16 clip) and show no seek bar;
* the focused result's full title is shown nowhere (tiles ellipsize, the info
  line has channel and length);
* the "Watch from your phone" header nearly touches its panel edge, and
  "Getting a code…" never resolves with these fixtures (pairing untested).

## Not tested, or not testable here

* **F1** The volume overlay is composited only by the TV display service
  (`src/display/service.rs`). QEMU apps draw to fbdev, so it never appears on
  screen; only the published buffer was checked. The gain is applied by the
  TV audio service, absent in `hello.qemu=1`, so loudness changes are not
  observable.
* Remote keys QMP cannot produce: KEY_OK (352), Exit (174), Info (358), Menu
  (139), color keys, Channel±, YouTube (569, the launcher's direct launch),
  Netflix. Their mappings were read in code only.
* Real thumbnails, live YouTube (deliberately not contacted), TLS, real
  panel/display/audio hardware, TV timing (QEMU Doom runs at about 5–7 fps).
* Doom: death/respawn, intermission, finale, actual two-player play by hand
  (covered only by the multiplayer check), options sliders.
* Slides image fixture, long-running playback, PID1 live reload with an app
  open (only the existing REPL check).
