Owner's selected policy
-----------------------
Count full starts even after successful Home startup. The practical event is
entry into the kernel boot image, including adb reboot and a full start from
standby. This board also reports software resets as AC_ON, so that register
cannot reliably distinguish unplugging from a software restart.

From a newly initialized journal:
  start 1: Lean preparation
  start 2: Lean preparation
  start 3: original MBOOT preparation
  start 4: Lean preparation; repeat the three-start sequence

Home success never resets the count. A resume that does not start a fresh
kernel does not increment it. The escape is one start, not a persistent mode.
Each start counts when its journal commit completes. For a deliberate escape,
wait for LEANBOOT choice on UART before cutting power again; unplugging before
the selector reaches storage cannot be counted. A cut during the journal write
can leave the previous valid record, so it is not guaranteed to count that cut.
Here "original" means the original kernel and MBOOT-prepared FDT/initrd, with
the same installed native Home, applications and network configuration. It
does not switch to slot b or restore the Google TV framework.

Implementation (current v4 container)
-------------------------------------
Of the boot images, only boot_a changes. Its Android v4 header, kernel-size field,
partition size and AVB metadata remain the original sizes. Only the first
128 KiB of the kernel field changes: a 3660-byte initial Lean stage, a
compressed 125008-byte network gate, a compressed copy of the original kernel
prefix and compact metadata fit there. The original prefix
compresses to about 1.3 KiB; the rest of the kernel remains byte-identical. Vendor and
generic ramdisk bytes come from the ordinary MBOOT load, rather than being
duplicated in the bundle. Their integrity is checked before Lean uses them.
The metadata reconstructs the required original image sections, and the existing
Os.withPrepared core performs the Lean FDT/ramdisk/bootconfig preparation.

The first three ARM instructions, emitted by the existing Lean ARM DSL, set a
private stack and branch into Lean Stage0. It validates and expands the gate
to 26000000; the relocated entry is one ARM branch at offset zero. The 128 KiB
bundle prefix is preserved at 40000000 before the original prefix is restored
over the entry image. The v4 80-byte manifest is at 40002000; the compressed
gate starts at offset 0x3000 and metadata expands to 40020000. Length and
corruption checks precede decompression. These are not secure-boot signatures.
The full reconstructed kernel is checked before either boot path is used.
Logic, decompression, validation, copying, journal codec and policy are Lean
compiled to C and ARM. Unsafe memory, CPU, UART and block calls remain colored
by MemoryM/HardwareM and centralized under Unsafe.

MBOOT still initializes DRAM, secure firmware, panel and storage and loads the
boot images. The default entry is its normal kernel handoff. No executable
MBOOT patch, environment hook, boot0 change, slot change or vbmeta change is
needed. The pre-existing Lean logo in MBOOT is preserved.

The stock-path fallback retains the original FDT and initrd. The larger Lean
preparation only starts after a counter update has been read back. Its initrd
and FDT workspaces are backed up; a returned preparation error restores the MBOOT inputs
and jumps through the stock path. Recovery/missing normal-boot metadata skips
the counter and Lean preparation. Invalid payload metadata selects stock where
the original kernel is intact; damage to the indispensable gate/kernel may
still require UART recovery. No software scheme can promise an unbrickable TV.

Counter storage
---------------
Two 512-byte records occupy upgrade's last two sectors:
  absolute LBA 3217fe and 3217ff
  offset 031ffc00 within the 50 MiB upgrade partition
Each record has magic/version, sequence, state, complemented fields and CRC32.
The inactive record is written and read back before proceeding. Inconsistent
or unreadable records and write/readback failure select stock. Both invalid
records remain in stock mode until reseeded; no invalid state is auto-erased.
The initial pair is sequence 0/state 0. A normal record sequence wraps at 32 bits.

The block bootstrap retains MBOOT's initialized card, timing and pads, but
executes its own bounded FCIE/DMA command logic in Lean. It calls no MBOOT
function. Before CMD24, a fresh CMD8 checks that the card uses its normal user
partition, 512-byte sectors and a disabled write cache. Writes are restricted
to the two journal LBAs. This is not an eMMC driver that initializes from reset.
An OTA that overwrites upgrade may invalidate the journal and select stock.

Exact entry ABI clarification
-----------------------------
V013's final transfer sets r2 to a stack-resident legacy tag list, not the FDT.
The original kernel and MBOOT use the finalized FDT at physical 23000000.
The selector preserves the original r2 for stock boot and inspects 23000000
for normal/recovery selection. Before Lean edits that tree, it preserves
64 KiB at 26410000; a returned preparation failure restores both this FDT
and the original initrd. The model now supplies the real legacy-tag ABI and
checks byte-for-byte rollback after an invalid FDT recipe.

Bounded DMA replacement and successful RAM boot
---------------------------------------------
An initial direct Lean CIFD implementation reproduced a CRC error but returned
to the MBOOT prompt. The first 64 bytes matched, while bytes after the first
FIFO chunk were corrupt. Replacing CIFD with the ordinary single-sector DMA
path produced an exact 512-byte match with MBOOT's independent read, status 0.
The former six assembly instructions for resident read/write calls are removed;
the audit at that checkpoint reported 24 private FFI declarations and 132 ARM
instructions. Signed network boot later added two crypto FFI declarations and
one call bridge (14 instructions), for current totals of 27 and 146.
Evidence: bounded-io/read-test.json and bounded-io/cifd-failure/.
The following journal trial advanced sequence 0/state 0 to sequence 1/state 1;
independent MBOOT readback verified the new record and unchanged other copy.
Evidence: bounded-io/journal-test.json and journal-before/after.bin.

The complete compact-lean-dma RAM trial then committed sequence 2/state 2,
printed LEANBOOT OS prep and LEANBOOT Linux, and reached native READY +19.30s.
Wall time from bootKL to READY was 26.67s. Root ADB independently confirmed

Installation and verification tools
----------------------------------
  nix develop -c python3 tools/bootloader/install-boot-image.py --apply
  nix develop -c python3 tools/bootloader/verify-default-tv.py

The installer requires the exact matching successful compact-lean-dma RAM
result and verifies the original target hashes before writing. The verifier
requires a fresh sequence-zero journal and performs four ordinary reboots;
it checks UART path/READY, boot IDs, journal CRCs and sequence, the Lean boot
property, Ethernet address and the installed boot_a hash after every restart.
It stops on the first mismatch.

UART rollback, only at an existing verified MBOOT prompt:
  nix develop .#bootloader -c python3 tools/bootloader/restore-boot-image.py
  nix develop .#bootloader -c python3 tools/bootloader/restore-boot-image.py --apply

The first command only loads and CRC-checks boot_b as the exact original
boot image. That read-only check passed. The second restores boot_a from
those verified bytes without changing slots, then verifies the readback.
The write rollback has not been exercised. The verified stock host backup
and the earlier proven UART-to-USB-Fastboot recovery path remain available.
