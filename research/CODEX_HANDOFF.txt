Main discovery: vendor libraries retain DWARF debug information
--------------------------------------------------------------
This was found late and is the most promising next research direction.
The native glibc midaemon and libmi.so retain .debug_info, .debug_str,
.debug_loc, source filenames/lines and named types. Exact field offsets,
struct sizes, enum values, function signatures and ioctl parameter types
can be recovered directly rather than guessed from strings/disassembly.

Artifacts under assets/research/firmware-implications/:

  mi-init-layouts.txt         Focused initialization struct/member layouts.
  midaemon.disassembly.txt    Actual native daemon ARM instructions.
  mstar_fbdev_mi.ko.disassembly.txt
  audio.primary.mt5867.so.thumb.txt
  extracted.json             Hashes of initial extracts.
  source-verification.json   Fresh backup SHA256SUMS comparisons.

The full native libmi.so used for DWARF is now staged at:
  assets/build/g06-platform/root/mnt/vendor/tvservice/glibc/libmi.so
LLVM tool used:
  /nix/store/8w308r33lb6d0ijmypa802v6dvyswkcj-llvm-21.1.8/bin/llvm-dwarfdump
Useful bounded command, from agent1:
  llvm-dwarfdump --name=MI_SYS_InitParams_s --show-children --recurse-depth=1 \
    assets/build/g06-platform/root/mnt/vendor/tvservice/glibc/libmi.so
Do not dump function children without a depth limit to the conversation:
their optimized location/call-site information is very large.

Concrete recovered types in this exact ARM32 glibc library:
  MI_SYS_InitParams_s: 96 bytes, DIE 0x000a0abe.
  MI_DEV_SYS_InitParams_s: 392 bytes, DIE 0x000a396d.
  MI_DISP_InitParams_s: 12 bytes; enum fields at offsets 0,4,8.
  MI_OSD_InitParams_s: 12 bytes; bWaitSync@0, bAutoFlip@1,
    eCanvasBufMode@4, u16SupportSurfaceCount@8, bWaitIdle@10.
  MI_SYS_ModuleInfoParams_s: 8 bytes, DIE 0x000a0a8a;
    eModuleId@0, bInited@4. This matches the framebuffer readiness query.
  MI_SYS_Init wrapper has an eIoctl constant -1048045568 = 0xc1881800.
    Its encoded size is 392, matching the DEVICE struct, not the public
    96-byte API struct. This is strong ABI evidence, not a tested ioctl.
  MI_DEV_SYS_Ioctl_e typedef at DIE 0x000a391a points to enumeration
    0x000a37bd. Follow DW_AT_type references for enum/typedef definitions.
Do not equate every MI_VIRT/MI_PHY typedef with a native 32-bit pointer;
follow the debug type graph and preserve actual 64-bit fields/alignment.

Firmware findings that change the platform plan
-----------------------------------------------
1. Exact mstar_fb_open calls mstar_FB_GetMiDaemonInitStatus at 0xb38 and
   returns -EINVAL at 0xb88 if not ready. The helper uses MI_SYS_GetAttr
   attribute 5 and a returned status byte. Merely loading modules is not
   sufficient; a ready flag must not be fabricated as a substitute for init.
2. Framebuffer probe reads /vendor/tvconfig/config/sys.ini and OSD INIs.
   OsdDefine.ini configures FBDEV0 at 1280x720, layer 1, format enum 8,
   FB_IOMMU=1 and FB_DFB_RESERVED=1. Actual RGB bitfields/page count remain
   unmeasured; enum 8 has not yet been mapped to a format definition.
3. sys.ini selects /tclconfig/hardware/param/soc/
   Customer_185_32TCON_B07-1_TL1P2.ini. Board-specific configuration matters.
4. mik_init.ini disables automatic DISP/OSD/AUDIO/AOUT/PCM initialization.
   Follow the native daemon's actual initialization order/arguments instead
   of assuming insmod completes panel/speaker setup.
5. The normal Android audio HAL PCM path calls MI_PCM_Open/Write and
   MI_AOUT_ConnectInput. It also has a separate tinyalsa mmap path. Direct
   pcmC0D0p speaker operation is not established. Android primary output
   policy is S16_LE stereo 48000 Hz; this is not an ALSA capability probe.
6. Native glibc libmi/libmi_server/libapiVDEC exist alongside Android's
   bionic libmi3/libOMX. They are useful native hardware-decode leads, but
   ABI recovery and buffer ownership remain work. Do not dlopen bionic
   libraries into the current static musl application.
7. .modinfo depends strings contain old utpa2k-system/avdec/frontend names.
   The shipped/live module is utpa2k. Actual imported/exported symbol
   resolution succeeds in the selected 13-module load order. Filenames or
   modinfo strings alone give a misleading dependency picture.
8. Earlier device-track work already supersedes agent1's fastboot boot
   instructions: no temporary boot handler was found in the inspected G06
   table; kexec load/unload worked but two actual handoffs failed. Read
   main/research/g06-ram-boot-status.md. Boot transport remains a hardware
   gate, separate from app/QEMU correctness.
