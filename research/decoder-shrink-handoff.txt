Reproduction
------------
Run Cargo from src/ to select the existing Rust 1.92 toolchain/config.
  cd src
  cargo build --release --target armv7-unknown-linux-musleabihf -p ytplay
  cargo build --release --target aarch64-unknown-linux-musl -p ytplay
  cd ..
  python3 tools/ffh264/check-formats.py
  python3 test/check.py -k framemd5
For full ARM32 coverage, run test/run.py faithful --headless --no-build
--mode framemd5 --timeout 300 with the offline replay server, then run
check_framemd5.py on serial.log and assert the log contains exactly 4431
framemd5 records. The existing comparator accepts a matching prefix, so
checking the complete frame count matters.

With current cached raw/preprocessed C inputs:
  python3 tools/ffh264/postprocess.py armv7-unknown-linux-musleabihf
  python3 tools/ffh264/postprocess.py aarch64-unknown-linux-musl
For fresh C/transpilation inputs:
  tools/ffh264/regenerate.sh
The latter uses eduardo-vm for c2rust; neither command is a TV action.

Regeneration incident and resolution
-----------------------------------
The first regeneration test found ignored pre-migration tus/raw paths still
pointing to app/decoder/ytdec.c. The old postprocess deleted its output tree
before noticing that invalid source path, leaving incomplete generated trees.
An archive overlay restore was rejected by automatic review because it could
replace uncommitted edits; that command was not executed or bypassed.
Instead, only the ignored cache manifests and cached ytdec files were migrated
to the current tools/ffh264/ytdec.c path. The staging/publish fix above was
implemented, then both trees regenerated successfully from those inputs.
The restored output exactly matches the pre-incident specialized snapshot.
Both source trees are complete again. Root was notified Cargo is safe.
No unresolved source-tree damage remains.

Remaining limits and next opportunities
---------------------------------------
This is a large mechanical reduction, not a small decoder ready for a full
Lean translation. It still includes FFmpeg allocation, threading, SPS/PPS,
CABAC/CAVLC, picture management, generic codec infrastructure, and duplicate
architecture-specific types. We kept C ABI/layout checks and unsafe code.
A sensible Lean boundary starts at bitstream parsing and pure leaf transforms,
then picture management; the existing small mp4/platform components remain
better initial proof targets than the entire generated decoder.
Further candidate shrinking: specialize 8-bit chroma dispatch to 4:2:0,
prune now-unreachable 4:2:2/4:4:4 branches, then remove unreachable generic
functions/types using stronger per-module reachability. Preserve rejection
before unsupported-format dispatch and broaden fixtures before larger cuts.
The assembly source includes variants the linker may now discard; it was
intentionally retained unchanged, as requested.

A separate pre-existing benchmark bug was exposed by a 4-frame positive clip:
player.rs conversion-only bench never flushes its final decoder and indexes
frames[0] when frame threading buffered every frame. Both actual decode-only
passes returned the correct 4 frames before that panic. The 64-frame format
fixture avoids this unrelated bug; root was informed. No ytplay source was
changed by this task.
