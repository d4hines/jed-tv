Local assets/research/g13-module-compat/ contains 36 passing consistency
checks. Both recovered TCL header sets reproduce stock module_layout CRC
a03a05bf. The new kernel's module_layout CRC is 3d611b88. All 33 saved ARM32
modules in each firmware have mismatched symbol CRCs against the new build.

This is a real ABI difference: stock Mali code increments task.usage at
offset 0x210, while the new kernel puts that field at 0x8. The stock task
structure is 2,432 bytes; the new one is 1,920. The missing ARM stack/current
implementation and additional changed types are documented in detail.
Matching CRC reproduction recovers a reference; it does not repair the ABI.

ARM64 assessment from the latest discussion
------------------------------------------

The G13 Cortex-A55 CPU supports ARM64. The pinned source contains
ARCH_MSTAR support under arch/arm64, a CONFIG_MSTAR_MT5867 machine entry,
and mstar2/hal/mt5867/cpu/arm64 platform/interrupt/SMP/power code. These are
source-availability observations, not a successful ARM64 build or boot.

An ARM64 route requires a valid AArch64 handoff from the bootloader/secure
firmware, ARM64 board bring-up and rebuilt or replacement kernel drivers.
The existing loader's verified entry is ARM32 SVC. Its current contract
cannot be assumed to enter an ARM64 Image. Linux's AArch64 boot requirements:
  https://docs.kernel.org/arch/arm64/booting.html

CONFIG_COMPAT can support retaining 32-bit userspace, subject to the vendor
ioctl and Binder interfaces. It does not permit loading the 32-bit kernel
modules in a 64-bit kernel. The current ARM64 elf_check_arch accepts
EM_AARCH64, and the module loader uses that check. The essential display/
audio stack is ARM32; the six ARM64 files included in each firmware are
alternate MediaTek Wi-Fi/Bluetooth modules, not ARM64 replacements for
Mali, mik or utpa2k. Keeping an older kernel version does not remove this
architecture mismatch.

A small ARM64 kernel/initramfs experiment would not require full AOSP.
Functional display/audio would still require the vendor driver work.
No architecture change or new build was performed for this assessment.

Boundary for a later physical trial
-----------------------------------

Read AGENTS.md, RECOVERY_NOTES.txt, research/G13_LEAN_BOOTLOADER.txt and
research/G13_LEANBOOT_DEFAULT.txt before changing boot state. Main records
hardware validation of the shared preparation core through the installed

the earlier standalone hardware-tested image is separately preserved.
research/G13_LEANBOOT_ETHERNET.txt also records a working RAM Ethernet
payload, not a firmware update service. Saved Ethernet/UART state and device
identity must be refreshed by the agent that actually receives TV access;
there was no live TV check in this work.

A bounded RAM-only UART/initramfs smoke test can investigate physical kernel
bring-up. It is a separate experiment from starting the stock Android/native
stack. The current Android/QEMU ramdisk and six initcall exclusions are not a
prepared physical-TV profile. A trial needs an explicit physical-board boot
profile, retained recovery access and owner coordination at execution time.
This handoff provides no flash command and does not authorize a persistent
installation. Stock modules must not be force-loaded to bypass the known ABI
differences. No claim of a working ARM64 TV image or complete Android 16 port
is implied by the available artifacts.
